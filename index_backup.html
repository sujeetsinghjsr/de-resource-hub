The Data Engineering roadmap

Follow a structured path. Build strong fundamentals first, then progress toward distributed processing and production pipelines.

01

Foundations

Learn SQL, Python, Git, Linux basics, relational databases, joins, aggregations, and data modelling.

Suggested: 3–5 weeks
02

Data pipelines

Build batch ETL/ELT workflows. Learn APIs, file formats, orchestration, data validation, and incremental loads.

Suggested: 3–5 weeks
03

Big data & cloud

Practice Spark, lakehouse architecture, cloud storage, warehouses, partitioning, and distributed processing.

Suggested: 5–8 weeks
04

Production engineering

Develop streaming pipelines, CI/CD, monitoring, security, governance, data quality, and performance optimisation.

        01 · Batch Processing
        
Enterprise Batch Data Pipeline


        

          Process large volumes of source data on a schedule, validate the
          results, and publish reliable datasets for reporting and analytics.
        


        
Data flow

        

          
Source Systems
DB / Files / APIs

          →
          
Ingestion
ADF / Airflow

          →
          
Raw Storage
ADLS / S3

          →
          
Transform
Spark / SQL

          →
          
Serving
Warehouse / BI

        


        

          How it works in practice
          

            
    
              
  • Ingestion: Extract new or changed data from source systems using scheduled jobs, APIs, files, or CDC.
    • 
              
  • Raw layer: Preserve source data and ingestion metadata so failed processing can be investigated or replayed.
    • 
              
  • Transformation: Use Spark or SQL to standardize schemas, join datasets, and apply business rules.
    • 
              
  • Validation: Check required fields, duplicate business keys, record counts, and reconciliation totals.
    • 
              
  • Publishing: Make validated datasets available to downstream applications, analysts, or reports.
    • 
            


            
Failure handling: Retry transient failures, isolate invalid records, alert on unresolved errors, and rerun safely using checkpoints or idempotent writes.


            

              Interview question
              
How would you design a batch pipeline that processes 500 million records every day?

              
Answer approach: Discuss incremental ingestion, partitioning, distributed processing, data skew, write strategy, reconciliation, monitoring, and recovery. Select partition sizes and compute resources based on actual data volume and performance tests.

            

          

        

      


      
      

        02 · Real-Time Streaming
        
Market Data Streaming Platform


        

          Ingest continuous market events, process them with low latency, and
          publish current prices while retaining data for downstream analysis.
        


        
Event flow

        

          
Exchange Feeds

          →
          
Java Producer

          →
          
Kafka Topics

          →
          
Stream Processing

          →
          
Redis / Oracle

        


        

          How it works in practice
          

            
    
              
  • Producers: Publish price events with fields such as instrument ID, exchange, bid, ask, event timestamp, and sequence number.
    • 
              
  • Kafka: Buffers events in durable topics. Choose partition keys carefully to balance parallelism and preserve ordering where required.
    • 
              
  • Processing: Validate event schemas, detect duplicates, handle late or out-of-order events, and apply transformation rules.
    • 
              
  • Redis: Can serve the latest price quickly to applications. Oracle or a suitable historical store can retain data for querying and reconciliation.
    • 
              
  • Monitoring: Track consumer lag, processing latency, malformed messages, throughput, and missing feed events.
    • 
            


            
Important design decision: Redis is commonly used for low-latency access to current values; it should not automatically be treated as the permanent system of record.


            

              Interview question
              
How would you prevent duplicate or out-of-order market price updates?

              
Answer approach: Use event identifiers or sequence numbers, define the ordering key, track processed events where needed, and reject stale updates according to business rules. Make downstream writes idempotent and define recovery behavior for replayed events.

            

          

        


        

          Portfolio connection: this architecture reflects a market-pricing
          pattern using Java, Kafka, Python, Oracle, and Redis.
        

      


      
      

        03 · Azure Data Platform
        
Azure Lakehouse Pipeline


        

          Combine managed orchestration, cloud storage, and distributed
          processing to deliver governed datasets for analytics.
        


        
Platform flow

        

          
Sources
DB / API / Files

          →
          
Azure Data Factory

          →
          
ADLS Gen2
Bronze

          →
          
Databricks
Silver / Gold

          →
          
SQL / BI / APIs

        


        

          How it works in practice
          

            
    
              
  • Azure Data Factory: Orchestrates ingestion, schedules, dependencies, parameters, retries, and pipeline monitoring.
    • 
              
  • ADLS Gen2: Stores raw and processed files, commonly in formats such as Parquet where appropriate.
    • 
              
  • Databricks: Uses Spark to transform data, enforce quality rules, and produce curated datasets. Delta Lake can provide transactional table operations.
    • 
              
  • Security: Apply Microsoft Entra ID, Azure RBAC, managed identities, and appropriate storage permissions. Avoid embedding credentials in notebooks or source code.
    • 
              
  • Operations: Log run IDs, input and output counts, processing duration, rejected records, and failure details.
    • 
            


            
Implementation pattern: Pass a batch or watermark parameter from orchestration to the processing job, persist its run status, and update the watermark only after the relevant data has been processed successfully.


            

              Interview question
              
What is the difference between Azure Data Factory and Databricks?

              
Answer: ADF primarily orchestrates and moves data between systems. Databricks primarily provides a compute environment for distributed transformations, Spark processing, and lakehouse workloads. They can work together in one pipeline.

            

          

        

      


      
      

        04 · Lakehouse & Data Quality
        
Bronze → Silver → Gold


        

          Separate raw ingestion, validated business data, and consumer-ready
          datasets so data quality issues can be traced and safely corrected.
        


        
Data refinement

        

          
Source Data
Batch / CDC

          →
          
Bronze
Raw / Replay

          →
          
Silver
Clean / Deduplicate

          →
          
Gold
Business Rules

          →
          
Data Products
Reports / APIs

        


        

          How it works in practice
          

            
    
              
  • Bronze: Keep source-aligned data and ingestion metadata, including source timestamps and batch IDs.
    • 
              
  • Silver: Apply schema checks, deduplication, standardization, reference-data joins, and record-level validation.
    • 
              
  • Gold: Apply business definitions and aggregations for reporting or downstream data products.
    • 
              
  • CDC: Process inserts, updates, and deletes using reliable change keys, ordering rules, and deletion handling.
    • 
              
  • Idempotency: Use stable business keys and controlled merge or upsert logic so a rerun does not create additional copies of the same logical record.
    • 
              
  • Data quality: Record rejected rows, reconcile source-to-target counts, and alert when thresholds are breached.
    • 
            


            
Example: If a trade references an instrument that is missing from the reference-data table, retain the rejected record and its reason, alert the relevant team, and reprocess it when the reference data becomes available.


            

              Interview question
              
How do you make a data pipeline safe to rerun after a failure?

              
Answer approach: Identify a stable business key, make writes idempotent, maintain run and checkpoint metadata, use transactional merge operations where supported, and reconcile outputs before marking a run successful. Handle partial failures and concurrent runs explicitly.

Prepare with confidence

            
Data Engineering interview prep

            

              Start with core concepts, then practise explaining trade-offs,
              failure handling, and production design decisions.
              Select a question to reveal a sample answer.
            

          

        


        

          

            
            

              ETL means Extract, Transform, Load: data is transformed before
              it is loaded into the target system. ELT means Extract, Load,
              Transform: raw data is loaded first and transformed inside the
              target platform, such as a cloud warehouse or lakehouse.
              ELT is common when the target platform can efficiently scale
              compute for transformations.
            

          


          

            
            

              An idempotent pipeline can process the same input more than once
              without creating incorrect duplicate results. Use stable business
              keys, deterministic transformations, deduplication, merge/upsert
              operations, and processing checkpoints. Record successful
              processing so retries can safely recover after failures.
            

          


          

            
            

              First inspect the Spark UI and execution plan to identify the
              slow stage. Check for data skew, excessive shuffles, small files,
              unnecessary columns, and inefficient joins. Filter early,
              select only required columns, use appropriate join strategies,
              tune partitioning, and broadcast genuinely small tables where
              appropriate. Compare execution metrics after each change.
            

          


          

            
            

              Identify the correct business key and decide which record should
              be retained, for example using an event timestamp or source
              sequence number. In batch processing, use SQL window functions
              or Spark deduplication. In streaming systems, define suitable
              event-time and watermark rules. Also investigate why duplicates
              occur rather than relying only on downstream cleanup.
            

          


          

            
            

              A data lake stores varied data formats and is often flexible
              for raw data, exploration, and large-scale processing. A data
              warehouse is designed for governed, structured analytical
              workloads. A lakehouse combines lake-style storage with
              capabilities such as transactional tables, schema enforcement,
              and analytical processing. The right choice depends on workload,
              governance, cost, and operational requirements.
            

          


          

            
            

              Define the source contract, ingestion frequency, volume,
              latency, and recovery requirements. Land source data durably,
              track run IDs and checkpoints, validate schema and records,
              and process data using safe retries. Make writes idempotent,
              quarantine invalid records, monitor freshness and failures,
              and provide alerts, reconciliation, and a documented replay
              strategy.
            

          


          

            
            

              Partitioning divides a dataset into smaller logical or physical
              groups, often by date or another commonly filtered column.
              It can reduce the amount of data scanned and help parallel
              processing. Poor partition choices create too many small files
              or skewed workloads. Choose partition keys based on query
              patterns, data volume, and the storage or processing engine.
            

          


          

            
            

              Define measurable checks for completeness, uniqueness,
              validity, consistency, freshness, and reconciliation.
              Run checks at ingestion and after transformations, track
              results over time, and alert on meaningful thresholds.
              Quarantine or block critical failures according to business
              rules. Keep audit information so the team can investigate,
              correct, and safely reprocess affected data.
